# NovaNet demo corpus

A synthetic knowledge base for a fictional carrier, **NovaNet Broadband / 星联宽带** (home broadband and mobile plans), in Chinese and English, and a question set with the expected answers. It exists to test retrieval on a document set that looks and misbehaves like a real one, which ten clean FAQ entries do not.

Everything is invented for this repository: the company, the plans, the devices, the 30 districts, the prices, the dates and the policies. There are no real companies, people, phone numbers, addresses or URLs. The files are generated by a deterministic Go program; nothing in this directory is derived from customer material.

## Generate

```sh
go run ./demo/novanet/gen -out /path/to/empty/dir -today 2026-10-27
```

The output tree is the object tree: a key is the path relative to `-out`, and it goes under `KB_S3_PREFIX` as it is. `products.yaml` is at the root, as the product catalog must be. Copy or sync the tree to the bucket, then run the usual `scan`, `parse`, `generate`, review and `publish` steps.

`-today` only moves the validity dates of the fact tables under `facts/`. Every other file is byte-identical whatever the date, so a regenerated corpus shows no change to `scan`.

```sh
go test -race -count=1 ./demo/...
```

The tests generate the corpus twice, parse every `.docx` and `.xlsx` with the service's own parsers, import both Q&A workbooks, validate the catalog, and check that every expected section in `questions.yaml` exists and contains its `fact`.

## Layout

| Path | Content |
|---|---|
| `products.yaml` | The product catalog (root, one file) |
| `facts/` | Fact tables with `.facts.yaml` (plans, topups, roaming_packs); written by `facts.go` |
| `{zh,en}/plans/` | One plan sheet per plan, plan comparisons |
| `{zh,en}/faq/` | Plan FAQ (near-duplicate questions), new vs existing customers, the Q&A workbook |
| `{zh,en}/policies/` | Contract and late-payment policies in two versions each, and 11 current policies |
| `{zh,en}/billing/` | Bill, payment, invoice, top-up guides and the one-off fee schedule |
| `{zh,en}/devices/` | User guides for R3, R5, R5 Pro, G1, G2, T2, T2 Max and M1, model comparisons, compatibility table |
| `{zh,en}/support/` | Troubleshooting articles for broadband, TV and mobile |
| `{zh,en}/network/` | 30 service-area pages, 12 maintenance notices, a coverage list |
| `{zh,en}/stores/` | 15 service hall pages and a hall list |
| `{zh,en}/promotions/` | 13 promotions, some expired |
| `{zh,en}/roaming/`, `sim/`, `app/`, `addons/`, `business/` | Roaming, SIM and account services, the app, add-ons |
| `{zh,en}/handbooks/` | Three long handbooks per language (18 to 30 topics each) |
| `{zh,en}/short/` | 16 one-answer pages per language |
| `{zh,en}/tariffs/` and other `.xlsx` | Reference tables read as content |

Some Chinese file names are Chinese, as on a real file server; the English ones are slugs. A file name that names a product tags its FAQs with it at publish time, so the plan sheets and device guides are named after their product.

The `.docx` files mark their headings in four different ways (outline level on a built-in style, on a Chinese style with numeric ids, directly on the paragraph, inherited through `basedOn`), chosen by file name. Tables are real tables.

## The tricky cases

- **Near duplicates that differ in one detail.** `faq/plan-faq` pairs every question for Plan 59 and Plan 59 Plus, and for Fiber 500 and Fiber 1000 (data, minutes, contract, cancellation fee, roll-over, router, installation, upload speed, roaming, eSIM). `faq/new-vs-existing-customers` does the same for new and existing customers. The plan sheets and the Q&A workbook repeat the same facts, and the three reset-button rows differ only in the number of seconds (R3 5, R5 8, R5 Pro 10).
- **A policy that changed, twice.** `policies/contract-and-early-termination-policy-v2` and `-v3` contradict each other on the cooling-off period (7 vs 15 days), the early termination fees, how the fee falls, free relocations (1 vs 2) and downgrading. `policies/late-payment-and-suspension-policy-v1` and `-v2` do so on the grace period, late fee, suspension and restoration. Every changed term starts with its effective period. The old versions also cover topics the new ones dropped: the renewal gift (v2 contract) and paper bills (v1 late payment).
- **A stale Q&A row.** The English and Chinese Q&A workbooks still say the cooling-off period is 7 days; the current answer is in policy v3. Their late-fee row was updated.
- **Expired promotions.** The summer roaming deal and the 2025 Mid-Autumn gift have ended and say so.
- **Long documents.** The three handbooks have 18 to 30 topics each. Three to eight sections per handbook are long (around 1300 characters) and hold one answer sentence among ordinary background. No section is near the 6000 character cut.
- **Short documents.** `short/` pages are a question heading and one answer; the whole document is the answer.
- **Thirty look-alike district pages.** Coverage, Fiber 1000 availability and installation lead time differ per district; three districts open in 2027 and two have no opening date. The same facts are in the coverage list workbook.
- **Tables.** Plan sheets, comparisons, LED tables of the devices, the fee schedule, roaming packs, the coverage list and hall list.
- **Names that differ by a word or a number.** Plan 59 and Plan 59 Plus, Fiber 500 and Fiber 1000, R5 and R5 Pro, T2 and T2 Max, Booster 10 and Booster 30. None is declared compatible in the catalog, so the guard drops the FAQ of the other one.
- **Fact tables.** `plans` has two rows for Fiber 500 (an old price ending yesterday, a new one starting today); `topups` has decimal keys written as text; `roaming_packs` is deliberately broken (an empty key), so lookups answer `FACT_TABLE_UNAVAILABLE`. The documents state current plan figures; the Europe pack price and the top-up bonuses appear only in the fact tables.

### The product catalog

`products.yaml` has 17 products. Each plan has its English name and the `NameZH` value from `plans.go`, plus spoken and written forms (`59块套餐`, `五十九元Plus套餐`, `光纤五百`, `光纤一千`). The families the guard knows are the leading Latin words of the aliases: plan, fiber, basic, r, g, t, m (`booster` and `senior` are also families, but they are longer than the five letters the guard's token rule reads). A question that names an unlisted model of a known family (`Plan 69`, `R7`, `G3`, `T3`, `M2`) is the unknown-model case and must be `NO_MATCH`. M1 is declared compatible with R5 and R5 Pro.

Known limits, kept on purpose and labeled in the questions: a three-digit model (`Fiber 800`) and a model written only in Chinese (`69元套餐`) cannot be recognized, `Booster 20` is not reached by the five-letter family rule, and the ASR slip `光线五百` and the spoken `五十九块` are not aliases, so the guard does not act on them.

## Questions: `questions.yaml`

Strict YAML (unknown fields are rejected). One list, `questions`, of:

| Field | Meaning |
|---|---|
| `id` | Stable, unique (`q-en-017`, `q-zh-204`) |
| `language` | `EN` or `ZH`; the search language of the call |
| `text` | What the caller says |
| `category` | `COVERED`, `PARTLY_COVERED`, `NOT_COVERED`, `OUTDATED_ONLY`, `ACCOUNT_SPECIFIC` |
| `tags` | Style tags, at least one: `colloquial`, `indirect`, `asr_error`, `mixed_language`, `spoken_numbers`, `near_duplicate`, `deep_in_long_doc`, `short_doc`, `product_confusion`, `unknown_model`, `needs_fact_table`, `table_lookup`, `policy_change`, `stale_source`, `qa_workbook`, `district`, `multi_step` |
| `expect` | List of `{file, section, fact}`. Any one of them is a correct hit. Empty means the right answer is `NO_MATCH` |
| `avoid` | Optional list of `{file, section}`: looks like an answer but is wrong (replaced policy version, stale Q&A row) |
| `factLookup` | Optional `{table, key}` of the fact table that also answers it; present exactly when the tag `needs_fact_table` is |
| `liveExample` | Optional; `true` marks a question for a live call |
| `note` | Optional; says why a label is a judgment call |

Matching an expected item to a stored section: `file` is the object key and `section` identifies the section in its `source_ref`, which `internal/parse` builds as the object key, `#`, and the parser's reference.

| Source | `section` | `source_ref` |
|---|---|---|
| `.docx` | heading path joined with ` > `, e.g. `Plan FAQ > How much data does Plan 59 include?` | `<key>#<section>#<ordinal>` |
| `.xlsx` content | the data range, e.g. `Halls!A2:C16` | `<key>#<section>` |
| Q&A workbook row | the row, e.g. `Quick answers!A14` | `<key>#<section>` |

So a stored `source_ref` matches an expected item when it equals `file#section` or starts with `file#section#`. The ordinal is left out because it only counts the sections of the file. `fact` is a substring of the section text (for a Q&A row, of the answer); a candidate from that section is right when its answer states the fact, which tells the candidates of one section apart. The categories mean:

- `COVERED`: a section answers it. A judgment call is explained in `note`.
- `PARTLY_COVERED`: the documents answer one part or need a fact table for the rest.
- `NOT_COVERED`: no document answers it, including unknown models.
- `OUTDATED_ONLY`: only a replaced policy version or an ended promotion answers it. The expected item is that old section, and a correct reply says it no longer applies.
- `ACCOUNT_SPECIFIC`: it needs the caller's own data, and the right answer is a transfer or the app.

The marked `liveExample` questions are three or four per language for each of: hit (`COVERED`), `NO_MATCH` (`NOT_COVERED` and `ACCOUNT_SPECIFIC`), and hits only the outdated policy (`OUTDATED_ONLY`), plus one partly covered question each.

## Run it end to end

The commands below load the corpus into a scratch deployment (its own database, S3 prefix and `KB_MEILI_INDEX_PREFIX`), then evaluate the service on it. `kb.sh` stands for any wrapper that runs `aicc-knowledge` with that deployment's `KB_*` environment.

```sh
# 1. Load. The fact tables live under facts/ and are loaded separately; keep them byte-identical.
go run ./demo/novanet/gen -out ./corpus -today 2026-10-27
aws s3 sync ./corpus s3://<bucket>/<prefix> --endpoint-url <endpoint>   # or any S3 client
kb.sh scan && kb.sh parse
#    every file version is PARSED except facts/roaming_packs.xlsx (FACTS_INVALID, on purpose)

# 2. Generate. Several processes claim jobs in parallel (FOR UPDATE SKIP LOCKED); match the LLM's slots.
for i in 1 2 3 4; do kb.sh generate & done; wait

# 3. Review. Edit the workbook, then import it; repeat per batch.
kb.sh export-review -out review.xlsx
kb.sh import-review -in review.xlsx -reviewer <name>

# 4. Publish both languages.
kb.sh publish -language ALL

# 5. Resolve the question set to candidate ids (read-only SQL against KB_DATABASE_URL).
KB_DATABASE_URL=... KB_S3_PREFIX=<prefix> go run ./demo/novanet/resolve \
    -questions demo/novanet/questions.yaml -out eval.csv -index index.json \
    -gaps gaps.txt -lenient-out eval-lenient.csv

# 6. Evaluate, in process and through the running service.
kb.sh eval -in eval.csv
kb.sh eval -in eval.csv -url http://127.0.0.1:18480 -api-key "$KEY"
kb.sh eval -in eval.csv -sweep
```

### The resolver

`eval` wants candidate ids, and ids exist only after generation, so `demo/novanet/resolve` joins `questions.yaml` to the LIVE publications. An expectation `{file, section, fact}` matches a published item when its `source_ref` equals `<KB_S3_PREFIX><file>#<section>` or continues it with `#`, and its answer (or question) contains `fact` after folding width, case and white space. All matching items are expected ids; a question with no expectation expects `NO_MATCH`.

An expectation that matches nothing is a gap. The resolver never relabels it. It leaves the question out of `-out`, lists it in `-gaps` with the candidates that did come from the section, and gives it a kind in `-index`:

| Kind | Meaning |
|---|---|
| `NO_CANDIDATE` | Nothing was generated for the section (generation gap) |
| `ONLY_REJECTED` | The section's candidates were all rejected in review |
| `FACT_NOT_STATED` | A published item comes from the section, but none states the `fact` verbatim (often a paraphrase) |

`-lenient-out` writes the `FACT_NOT_STATED` questions with every published item of their section as the expected ids. It is a supplement for judging how much of a gap is only wording; it never replaces the main CSV. Score the gap questions as misses to count a covered question that cannot be answered against recall.

`eval -json` reports aggregates only. For per-category and per-tag figures, run the questions through `POST /v1/search` and join the results to `-index` on the question text and language.
